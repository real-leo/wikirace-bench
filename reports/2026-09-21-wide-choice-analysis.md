# Laya / SemIf 扩展到单次 255 候选的可行性

2026-09-21，M1 Max / 32 GiB。结论：**两者都已实际跑通原生单次 255 项评分**，
但扩大候选数带来的速度和质量收益不同。之前的 512-token / 16-option 设置不应被理解为
不可突破的底层模型上限。本次仅做离线验证，正式长测适配器和下载模型均未修改。

## 结果

固定输入是上一轮 Jev 在三道题首步选出的 255 个候选；两种本地模型使用同一批保存的数据。
这里已经经过 Jev 预筛选，因此不代表独立完成整页检索或 WikiRace 的结果。

每个方法计时三次，表中为中位数（秒）；同一后端内使用相同紧凑提示，只改变分组/直选方式。
先预热小组和长请求，计时包含准备、原生评分和结果映射，排除模型加载及网页操作。
小组方法仍为串行，不代表其可达到的最佳批量吞吐。

| 后端 | 快照 | 小组淘汰耗时 | 单次 255 项耗时 | 小组耗时 / 直选耗时 |
|---|---|---:|---:|---:|
| Laya | DNA | 1.705 | 0.403 | 4.23× |
| Laya | Music | 1.615 | 0.373 | 4.33× |
| Laya | WWII | 1.800 | 0.506 | 3.56× |
| SemIf | DNA | 10.277 | 10.147 | 1.01× |
| SemIf | Music | 9.905 | 9.034 | 1.10× |
| SemIf | WWII | 10.551 | 10.372 | 1.02× |

255 项的 Laya 小组方案调用 37 次（32 + 4 + 1），SemIf 调用 17 次（16 + 1）；
直选方案均只调用一次。减少调用次数没有按比例降低 SemIf 耗时：长请求仍需要处理所有
候选文本，原来的串行方案也复用了公共状态前缀。这里观测到的 SemIf 收益约为 1%–10%，
小样本不支持宣称显著或稳定的吞吐改善。

## Laya：同时提高两个预算

本地发布配置：`max_len=512`、`head_max_len=192`；编码器配置为
`max_position_embeddings=8192`。`max_len` 控制整个请求，`head_max_len` 控制指令和选项区。
只提高 `max_len` 会让选项区继续被裁剪；需要同时提高，并审计最终实际输入。

本次在内存中使用：

```python
# 完整标题只放在选项区一次，状态保留目标、当前页和简短历史
agent.cfg["max_len"] = 4096
agent.cfg["head_max_len"] = 3584
```

带少量候选上下文的附加容量检查使用 `max_len=8192`、`head_max_len=7800`。
不修改权重、不重新训练，不修改模型文件。上游的选项得分来自各选项标记位置，
并非固定只有 8 个输出神经元，因此选项数量本身无需扩建模型权重。

| 255 候选快照 | 紧凑格式：标题一次 | 标题 + 短上下文 | 原重复标题格式所需 tokens |
|---|---:|---:|---:|
| DNA | 2,074 | 3,885 | 7,887 |
| Music | 1,964 | 4,183 | 8,041 |
| WWII | 2,506 | 4,621 | 8,900，超过 8,192 |

前两种格式均完成 GPU 推理，所有 255 个标记和完整标题保留，没有隐式截断。
第三列重复格式仅计算容量，不作为速度表中的输入。此前“小组很小”的一部分原因
确实是适配格式开销，而不是候选标题本身必须占那么多空间。

底层位置范围支持更长输入，不等于当前决策模型在长输入和大选项集合上具有可靠质量。
本次也没有重新拟合概率校准参数。上游模型卡同样讨论了大选项集的预算问题和扩展设置：
[Laya 模型卡](https://huggingface.co/convaiinnovations/laya#honest-limits)。

## SemIf：扩展单-token 答案编号，而非简单改成 1–255

固定版本上游使用 `LETTERS = "ABCDEFGHIJKLMNOP"`，验证选项数为 2–16。
选项的分数取自下一 token 的对应词表位置。这是决策接口的编码约定，
不是 Qwen3.5-4B 只能读取 16 条内容。
[上游编码与验证](https://github.com/TheoLeeCJ/SemIf/blob/ca3ba65f142967030ecb453346e94d6f476a69df/src/semif_phase1/core.py)。

直接用整数 0–254 并保持“一 token 评分”会出错：本地 tokenizer 中只有 0–9 是单 token，
例如 `127` 被编码为三个 token。本次从大写字母及字母组合中找到了足够的单-token 编号，
选择 255 个唯一编号（A、B、…、AA、AB、…），逐一验证：

- 编码后恰好一个 token，解码后精确还原。
- 255 个 token ID 互不相同。
- 接在每个完整提示后仍保持同一 token 边界。

将内存中的编号表扩展到 255，并把系统指令中的 “uppercase letter” 改成 “uppercase code”。
仍用上游 SerialPrefixScorer，直接读取全部编号的下一-token logits，按同组选项归一化。
没有改成生成长答案，也没有添加随机初始化的输出层。

| 255 候选快照 | 标题格式：实际 GPU 推理 tokens | 原完整候选上下文格式：仅 token 计数 |
|---|---:|---:|
| DNA | 4,018 | 10,387 |
| Music | 3,859 | 12,367 |
| WWII | 4,370 | 14,663 |

GPU 测试把应用输入上限提高到 8,192。保留原来每条的完整上下文则需要约 10K–15K tokens，
本次只做编码容量检查，没有对该长格式执行 GPU 推理。Qwen 官方标注更大的原生上下文范围，
但模型理论长度不代表本机在该长度下的内存、速度或正确率已经验证。
[Qwen3.5-4B 模型说明](https://huggingface.co/Qwen/Qwen3.5-4B)。

## 255 项能计算，不代表会选择正确目标

做了九个很简单的合成检查：每个快照保留 255 项，把其中一项替换为目标文章标题，
分别放在第 1、128、255 个位置，要求模型选出它。特殊候选 ID 为
`injected-exact-goal`，便于记分；它也会出现在 Laya 的选项标签中，因此这些是诊断检查，
不是无提示的真实页面准确率测试。SemIf 的候选 ID 不出现在其选项描述中。

| 后端 | 小组淘汰找到目标 | 单次 255 找到目标 |
|---|---:|---:|
| Laya | 3/9 | 1/9 |
| SemIf | 8/9 | 9/9 |

Laya 直选只在 Music 目标放最后时选对；WWII 的小组方案三种位置都选对，直选均未选对。
这表明当前 Laya 的 255 方案虽更快，尚未通过基本质量验收；小组方案本身也不够可靠。
不能把这些失败全部归因于扩窗，提示、模型能力、选项位置和淘汰策略都可能参与。

SemIf 通过了九个检查；其中 Music 目标放第一位时，小组淘汰失败而直选成功。
这只证明本次简单检查中 255 个编号的读出和目标识别可用，不能推导出长程 WikiRace
成功率。真实首步没有目标时，两种策略选择的下一跳也发生了变化。

本次峰值 MLX 分配：Laya 1,658.40 MiB，SemIf 12,774.73 MiB；这不是整个进程 RSS。
所有推理输出均通过候选数、编号映射、有限分数和完整输入审计。

## 实际建议

- 可以增加一个实验性的原生 255 选项模式，不能继续把默认 512 / 16 当作不可调整的硬限制。
- Laya 的速度收益明确，但先解决当前任务上的质量问题，再考虑替换正式模式。
- SemIf 的 255 方案在这次基础检查中更有希望，但仅扩大选项数没有带来成倍提速。
  值得继续比较 32/64/255 项、同轮小组批量执行，以及精简上下文的质量损失。
- 一次请求的候选数、输入 token 上限、GPU 每批并行请求数是三个不同参数。
  把候选数改成 255 不等于同时获得高吞吐、正确选路和 Jev 的端到端表现。
